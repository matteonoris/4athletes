  totals. `20261005173224` fixes attendee validation; `20261005174556` preserves
  edits to an athlete's own historical sessions after leaving and notifications

  Team Batti has Battista Tomasoni as its manager.
- Existing invitations were replaced by random 128-bit codes. Managers retrieve
  the current code from the app. Old invitation codes no longer work.
- New team creators must be coaches and become managers. Athletes join using a
  server-validated code; coaches remain pending until manager approval. Coaches
  can have several memberships; an athlete can have one active team. Direct
  profile role/team updates and direct membership writes are denied.
- Managers can approve/reject requests and promote/demote/remove members. The
  team row is locked during transitions; the last manager cannot leave or lose
  the role. Actor, subject, previous/new state and server time are recorded in
  a private audit table. Initial bootstrap records represent owner-approved
  administrator work rather than an authenticated in-app actor.
- Coaches can read their currently authorized athletes' personal health data.
  Only the owner can change physical measurements, sleep, HRV and wellness
  scores. The explicitly whitelisted manually recorded sports tests (sprints,
  balance, plank, pullups and Léger results), PRs, jumps and non-imported workouts
  remain coach-editable. Coaches cannot modify `health_sync`/`imported` sessions.
- Calendar reads are filtered on the server by stable account IDs and current
  membership. Athletes receive only their own attendee entry and can patch only
  their own response/performance. Invites to unrelated athletes and cross-team
  event changes are rejected. Notification recipients/content are generated by
  the server; recipients may mark read or delete their own notices.
- Teammate directory excludes email, birth dates and physical/health fields.
  Leaderboards return numeric totals for the selected period, with no session
  payload, raw HR samples, private notes or location. Existing athlete/coach
  modular ski payloads and monthly SL/GS/SG/DH/SX reports are preserved.
- `avatars` is private, accepts JPEG/PNG/WebP up to 5 MB, and restricts writes to
  the account UUID folder. Owner/current teammate reads use signed links lasting
  30 minutes. The profile stores the object path, not an expiring signed link.
- Server profile registration and changed birth dates enforce the declared
  minimum age of 14. This verifies declarations, not the person's actual age.
- Invitation attempts are limited to five per account per minute. Invalid
  attempts return a result rather than raising, so the counter commits.

## Verified audit — 5 October 2026

Project: `hqzushizdfxrnktoqbtr` (4Athletes). Inspected through the project MCP.
This is the initial audit; the applied state and verification are documented above.

- Eight public tables have disabled RLS. The `anon` role can SELECT, INSERT,
  UPDATE and DELETE on profiles, teams, training sessions, body metrics, PRs,
  jumps, calendar events and notifications. Authenticated isolation also needs
  server enforcement. The consent table already has own-account protection.
- Profile saving currently upserts `role` and `team_id` directly. Team joining
  looks up the invite code client-side and updates profile membership and the
   member count in separate requests. A table policy must not trust these
  client-controlled relationships as sufficient evidence of coach authority.
- Teams have no owner/manager column or separate verified membership registry.
  Of five teams, three currently have no associated coach, and one has multiple
  associated coaches. Establish authorized managers before assigning ownership;
  do not infer ownership from team names or arbitrary existing associations.
- The calendar loader retrieves all events before filtering in the app. Its
  invitation matching accepts IDs, email or names. Server access must use stable
  account identities and verified memberships, not name matching.
- Coach PR editing, athlete attendance and coach-created notifications are real
  supported workflows. A uniform own-user policy would break those workflows.
- The team leaderboard reads teammate profile fields and training sessions.
  Provide a restricted directory and summary endpoint, rather than granting
  teammates access to complete profiles, health metrics or session details.
- No Storage buckets or Storage policies are present in this project. The app
  nevertheless uses an `avatars` bucket and public URLs. Provision private image
  storage with owner/team permissions and adapt image retrieval accordingly.
- Aggregated readiness check: 29 profiles, 8 declared coaches and 21 athletes;
  no missing birth dates, under-14 declarations or dangling team references.
  This validates stored declarations, not ages or past authorization integrity.
- Security advisors still report eight RLS errors and disabled leaked-password
  protection. No individual health records were inspected or exported.

## Implementation order

1. Close anonymous access on personal tables and set safe default privileges
   for future objects. Keep Supabase Auth sign-in/registration functional.
2. Establish protected team membership and team managers. Bootstrap existing
   managers from owner-confirmed mappings; protect roles and relationships from
   direct profile updates. Choosing the coach role alone grants no authority
   over an existing team's athletes.
3. Replace direct team creation/join/leave/removal with validated server
   operations. Validate invite codes on the server, keep them out of general
   listings, generate secure invitations, enforce membership transitions and
   update member counts atomically. Coach invitation/approval is an owner
   decision still pending.
4. Apply operation-specific RLS for own athlete records, authorized coach/team
   reads, approved sports-record edits, targeted calendar access and recipient
   notifications. Use restricted server operations for attendance, invitation
   changes and notification creation. Do not allow changes to record ownership
   or arbitrary recipients. Define separately which health measurements a
   coach may change; the owner's decision is pending.
5. Add the restricted teammate-directory/leaderboard output and private avatar
   access. Enforce minimum signup age on the server as well as in the client.
   Maintain Matteo's operational access through protected administration, never
   through a privileged key embedded in the mobile app.
6. Strengthen the admin account with MFA; check Auth abuse/rate limits and leaked
   password protection availability. Keep privileged credentials and signing
   materials outside client code and version control.
7. Verify allow/deny behavior before applying the production rollout. Adapt
   Flutter to the new server operations first, test database policies with
   isolated fixtures/rolled-back transactions, and use an atomic reviewed
   production migration. Recheck advisors, then run actual-device checks and
   rebuild the signed AAB. Coordinate with existing iOS/Android versions that
   still use direct team/profile writes.

## Required verification matrix

| Actor | Allowed | Must be denied |
|---|---|---|
| Signed-out client | Auth flows and public privacy/deletion pages | Personal table reads/writes and private files |
| Athlete A | Own profile, logs, sessions and targeted invitations; approved team summaries | Athlete B's health/details, arbitrary team/role changes, forged ownership |
| Coach A | Authorized team's athlete reports and explicitly approved management actions | Team B's personal data, self-assigned membership, unauthorized health edits |
| Team manager | Controlled member/coach invitations and management in owned team | Ownership transfers or management of unrelated teams |
| Notification recipient | Own notifications and read state | Arbitrary recipient/content changes or forged notifications |
| Consenting health importer | Own device imports after consent verification | Imports after revocation, cross-account import writes |

Test direct SQL/API access, not only the screens: SELECT/INSERT/UPDATE/DELETE,
role/team escalation, cross-team IDs, attendee spoofing, stale sessions, private
image access, simultaneous joining/leaving and existing-client compatibility.
